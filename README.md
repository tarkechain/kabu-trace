# Webサイト要件テンプレート一式

Claude Code で Web サイトを制作するための汎用テンプレートである。案件ごとにこのディレクトリの中身をリポジトリ直下へコピーし、プレースホルダ {{ }} を埋めて使用する。

## ファイル構成

```
CLAUDE.md                     恒久規約。Claude Code が毎回自動で読む
docs/requirements.md          目的、スコープ、要件、受け入れ基準
docs/design-tokens.md         視覚仕様の数値（色、フォント、余白等）
docs/tasks.md                 実装タスクの台帳。/plan-tasks が生成する
docs/decisions.md             決定の経緯。必要時のみ参照
.claude/commands/             スラッシュコマンド定義
```

分割の軸は「変更頻度」である。CLAUDE.md は案件開始時に一度、requirements.md と design-tokens.md は壁打ち中に頻繁に、tasks.md は実装中に、decisions.md は判断時のみ更新される。

## 使用手順

1. このディレクトリの中身をリポジトリ直下へコピーする。
2. CLAUDE.md を記入する。技術スタックとコマンドが埋まっていれば十分である。
3. docs/requirements.md と docs/design-tokens.md に、現時点で決まっていることだけを記入する。決まっていない項目は {{未定: ...}} のまま残す。空欄にはしない。
4. Claude Code を起動し、Shift+Tab でプランモードに入る。
5. /kickoff を実行する。未決項目について質問が返るので、一問一答で決めていく。決定内容は自動的に文書へ反映される。
6. 未決がゼロになったら /audit を実行する。文書間の矛盾・曖昧さ・網羅性を検査する。重大な指摘が0件になるまで /kickoff と往復する。
7. /plan-tasks を実行する。docs/tasks.md が生成される。内容を確認し、不要なタスクや順序の誤りがあれば指摘して再生成させる。
8. /build を繰り返す。1回につき1タスクが実装され、検証結果が報告される。
9. 全タスク完了後、/verify を実行して受け入れ基準を検証する。

## 要件書の品質を測る方法

壁打ちが一巡したら、新しいセッション（文脈をクリアした状態）で docs/ 配下の文書のみを渡し、実装計画を書かせる。出てきた計画が意図とずれていれば、そのずれは文書の記述不足である。会話で補った内容に依存していたことを意味するため、該当箇所を文書へ追記して再テストする。同一セッション内での確認は、会話に残った文脈が補ってしまうため検証にならない。

## テンプレートの改善

/kickoff で実際に質問された内容は、テンプレートに不足している項目の一覧そのものである。案件が終わるたびに、質問された項目をテンプレート側の見出しとして追加する。数案件繰り返すと質問数が減る方向に収束し、汎用性が実測で高まる。

## 設計上の判断

- 受け入れ基準と非機能要件には EARS 記法（WHEN 条件 THE SYSTEM SHALL 挙動）を用いる。曖昧さを構文レベルで排除し、各要件をそのまま検証項目へ変換するためである。目的・スコープ・情報設計・デザインには適用しない。形式が適合せず冗長になる。
- 要件には R-1.1 形式の番号を振り、タスクとコミットメッセージから参照する。実装漏れを機械的に検出するためである。
- 作業手順は文書ではなくスラッシュコマンドとして実装している。文書は読み飛ばされうるが、コマンドは実行の有無が明確であり、手順の再現性が高いためである。
- design-tokens.md を独立させている。既存の仕様駆動開発フレームワークは視覚仕様を事前の成果物として扱わないが、Web サイト制作では見た目が主要な失敗要因であるため分離している。
